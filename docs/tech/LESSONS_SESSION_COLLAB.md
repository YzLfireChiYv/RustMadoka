## C19. 探索/主线推进：重要功能、向后排期、默认可配置（禁止产品写死原版常量当唯一真理）

| 字段 | 内容 |
|------|------|
| **触犯记录** | 2026-08-07 导出分析后，主人钉死产品口径 |
| **内容** | 原版 `secret` 将目标篇章写死为 `FIELD_CLEAR = 612001`（舞台装置の魔女），队伍写死 `partyDataId=1`，战斗结果写死胜。分析时以该模块为**机制样例**是正确的。主人要求：此类「推进主线/探索」属于**我们需要做的重要功能之一**，排期**向后**；实现时**不写死那么多内容**，提供**默认配置**，并允许用户（或作者）**自行配置**。 |
| **损失 / 负面影响** | 若把 612001 写死进产品：版本更新后新记忆之窗无法覆盖；若把分析文档里的整条链硬编码进 UI：维护成本爆炸且与「无脑 + 可配置」冲突。若因「重要」就立刻开工：挤占 E1/AUD-COMMS 等已定序，且在数据面与配置模型未稳时易半成品。 |
| **新规则** | （1）功能地位：**重要**，TASKBOARD/INVENTORY 记为 **LATER / 点名后开工**，默认不抢当前实现队列头。（2）设计约束：目标篇章（或「推到哪」）、队伍选择、是否处理迷宫/战斗点类型、门禁默认关等，一律 **配置项 + 合理默认值**；默认值可以取自原版行为（如历史上的 612001 链），但代码路径必须读配置。（3）实现前仍须 E1/E2 类数据与 mst 图可核对。（4）与 `clear_dungeon_event`（已通关隐藏事件）分模块/分配置描述，禁止混名。 |
| **理由 / 原理** | 游戏内容随版本增篇；写死 id 会在几个版本后失效。默认可配置保留「开箱能用一条稳妥链」，自行配置服务作者与进阶用户。向后排期是因为：依赖探索数据管道、队伍 UX（C10）、像客户端节奏、门禁与误推进度风险，这些底座未齐时先写死实现会返工。分析原版硬编码是为了**理解机制与默认值从哪来**，不是为了把硬编码原样上升为产品契约。 |
| **源码/log** | tool.py `FIELD_CLEAR` · export-data-analysis · TASKBOARD 修订 · 本 log |
