## 1. 参与与互斥

### 1.1 参与条件

1. 同一**用户组**内多张**游戏账号卡片**。  
2. 必须**同一服务器（同一 channel）**。  
3. 人数 ≥ 2；上限参考 `multiRaidConfig.maxJoinUserCount`（样本常见 10，以配置为准）。  
4. 房间开放范围：用户**首次必须自选**；程序**不提供**「未选择」也能开跑。  
5. **「仅自己」** 开放范围：**禁止**用于组队互援（无法相互支援）；校验失败则整任务不启动。  

### 1.2 任务互斥与停止权

1. 组队 Raid 进行期间，**每一个参与账号**都视为正在执行实际打服任务。  
2. 这些账号**不得**再并行清日常、单模块、洗词条、其它组队等（`TaskGate`：channel + 引继）。  
3. **仅发起该次组队任务的用户组**有权停止其中某一参与账号的当前任务，或停止整次组队任务。  
4. 其它用户组若挂有同一游戏身份：只能看到占用/「在用户组 X 组队 Raid 中」类展示，**不能**停止该任务（与 MULTI_GROUP 跨组只读占用一致，并在此补停止权）。  
5. 实现：任务登记带 `owner_group`；停止 API 校验请求用户组 == `owner_group`。

### 1.3 不刻意限速

重构版本**不**为「多账号像真人」而插入固定等待秒数。请求按协议与编排顺序发出即可。通讯节奏类审计（AUD-COMMS）另案，不挡本功能。

## 3. 一轮完整流程（n 人，逻辑须严谨）

设本轮仍有召唤次数的账号集合为 `S`（|S|≥1）。本轮实际开房账号为 `H ⊆ S`（每人至多开 1 房）。

```text
阶段 A — 魔女召唤（对每个 h ∈ H）
  1. 检查服务端剩余次数 / 无更多次数反馈；无次数则该号本轮不开房。
  2. 体力不足：优先 recover_stamina（剩余恢复次数可读）；仍不足则该号本轮结束召唤。
  3. initialize_stage 开房 → 读 multiRaidStageData.hp（总血量）与 multiRaidStageDataId。
  4. send_rescue（用户所选开放范围）。
  5. 按 §4 为「房主 + 本轮将援助该房的账号」拆分伤害；房主 add_damage + finalize。

阶段 B — 相互援助
  对每个已开房 r：
    每个账号 a ≠ r.host：入房援助一次（房间 id），伤害为 §4 分给 a 的份额。
  3 人且 3 房时：每人援助 2 次（其余两人的房各一次）。

阶段 C — 舔盒领奖
  在支援全部完成后、下一轮召唤开始前：
  各参与号领取可领的团战奖励（receive_reward）。
  默认不 retire；若用户开启「援助后退出」再对援助侧 retire（无结算奖励风险，仅可选）。

阶段 D — 是否继续
  若仍有任一方可召唤，或上一轮有人开房成功 → 进入下一轮；
  直到：累计/各自达到服务端日上限（样本 maxPlayCountPerDay 常为 6，以 game_config 为准，禁止产品写死 6），
  或全员得到「没有更多次数」类反馈且无人可再开房。
  特例：最后一轮仅 A 能召唤，B、C 仍可正常援助 A。
```

体力与次数不珍贵：边角不足则该号正常结束，不为小概率纠缠。

## 4. 伤害拆分（相对原版的优化 · AI 自定终稿）

### 4.1 原版对照

- 日常召唤/援助：配置 min–max **绝对值** `random.randint`（与血量无关）。  
- 魔女救世秒伤：可对 `raid.hp` **整段打满**。  
- **无**「按人数百分比上下限」公式；精确计算在本产品自定。

### 4.2 产品规则（保证能动手者打完后 boss 必被打满）

设组队名单人数为 **n**（2≤n≤10；n&gt;10 拒绝开跑）。  
开房回包 **boss 总血量** `H`（`multiRaidStageData.hp`）。

对每个造成伤害的账号（开房与援助同一套）：

| 项 | 公式 |
|----|------|
| 每人下限 | `⌊0.10 × H⌋`（至少 1） |
| 每人上限 | `⌊(1.10 − 0.10×n) × H⌋`（且 ≥ 下限） |

**目标和** `T = H`：全体动手者伤害之和 **Σ ≥ H**（整数上用残差分配保证，禁止「能支援的都支援完了 boss 还活着」）。

**算法（实现真源：`group_raid.rs` · `split_group_raid_damages`）：**

1. 前 n−1 人在 [下限, 上限] 内均匀随机。  
2. 第 n 人 = `T − Σ前`；若落入区间则接受。  
3. 否则拒绝采样（有限次）；仍失败则：先按比例压入区间，再把 **Σ 相对 T 的不足** 补给「未达上限」的人，直到 Σ≥T 或无人可加。  
4. **体力不足可完全跳过该号**：按**实际动手人数 k** 用同一公式重算（n 换 k），再分配；跳过者不占伤害份额。  
5. 单次 `add_damage` 可按原版 `DAMAGE_ONCE` 切片。

### 4.3 明确不考虑

- 体力用完不作为组队失败条件，不为体力做复杂规划。

## 6. 设备身份：`device_id` 按游戏账号卡片复用

| 项 | 规则 |
|----|------|
| **复用键** | 游戏账号卡片 = channel + 引继码（与 token 缓存一致） |
| **存储** | 优先写在该号 `cache/token/{引继}_{pwdMD5}.json` 的 `device_id`；并落 `cache/device_by_account/{channel}_{引继指纹}.json` 以便 token 重建后仍绑同一卡片 |
| **禁止** | 全数据文件夹共用一个安装级 `device_id` 给所有卡片（旧 `device_profile.json` 不再作为新号来源） |
| **不同卡片** | 必须不同 `device_id` |
| **同卡片再登录** | 必须复用该卡片已有 `device_id` |
| **与组队关系** | 多号并行时会话 uuid 仍分账号；device_id 分卡片后更接近「多角色设备登记」。不为此插入人为等待。 |

文档同步：`SDK_AND_LOGIN.md` §设备身份。

## 9. 验收（不写 FIXED 除非点测）

1. 2+ 同 channel 账号：一轮中每人开房后，每人援助次数 = 本轮开房数 − 自己是否开房。  
2. 舔盒在援助后、下一轮召唤前。  
3. 仅一号有次数时，其它号仍能援助。  
4. 次数以服务端为准停。  
5. 参与号 TaskGate 占用；仅发起用户组可停。  
6. 不同卡片 token 中 `device_id` 不同；同卡片重建 token 后仍同 id（device_by_account）。

### 8.1 创建入口（主人钉死 · 2026-08-08 **最终纠正**）

1. **「添加游戏账号」只负责添加游戏账号卡片**（别名 + 日服/国际服 + 引继 + 密码）。**禁止**在「服」下拉里加入「组队 Raid」与日服/国际服假平级。  
2. **组队不能只有单一全局入口**：不同用户需要**不同数量**的组队配置。  
3. **借用「游戏账号卡片」的设计**：组队配置以**卡片形态**（或从某张卡进入设置面板）管理；需要几套组队就有几份配置/几张组队卡，在主页卡片区呈现与操作。  
4. 设置面板内：勾选参与的**游戏账号**卡片、开放范围、队伍、援助后退出等（§8.2–8.4）。  
5. 运行时删卡取交降级；单号打满日次数。  
6. CLI 对等（P23）。任务书：**`docs/PLAN_GROUP_RAID_UI.md`**（状态：**CODE**，待点测）。  

**错误实现史：** 曾把组队塞进添加账号类型下拉 / 单独大折叠——**已回退**（log `2026-08-08-group-raid-ui-revert-handoff`）。**正确实现：** 主页组队配置多卡片（log `2026-08-08-group-raid-cards-wire-audit`）。

### 8.2 人数与「单号自动打满日次数」

| 勾选人数 | 行为 |
|----------|------|
| **≥2** | 完整组队：召唤 → 互援 → 舔盒 → 循环，直到各号服务端日上限（样本常为 **6** 次/日，以 `game_config` 为准，**禁止写死魔法数 6**；UI 文案可写「打满今日次数」） |
| **1** | **允许**。该号在单人模式下**自动打完今日可用召唤次数**（服务端上限，常为 6）：自开房 → 自打伤害（Σ≥H）→ 舔盒 → 下一轮，直到无次数。开放范围若为「仅自己」仅允许单号模式；多号时禁止「仅自己」（§1.1）。 |
| **0** | 禁止开始；人话提示先勾选卡片。 |

### 8.3 删卡自动降级

1. 运行**开始前**：参与名单与当前用户组卡片取交；被删卡片**不参与**。  
2. 若删后剩余 **≥2** → 按多号组队继续（人数 n 变小，伤害按新 n 拆）。  
3. 若删后剩余 **1** → **自动降级**为 §8.2 单号「打满今日次数」模式，不整任务硬失败。  
4. 若删后剩余 **0** → 任务不启动或立即结束，文案说明「参与账号均已删除」。  
5. 运行**进行中**某卡被删：该号已登记占用结束；其余号按 2–4 降级规则继续（实现时在编排循环头重新解析名单）。
