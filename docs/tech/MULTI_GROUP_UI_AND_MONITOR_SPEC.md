## 2. 面向新的、更详细的浏览器网页前端同步需求与多用户组需求：底层重构原则

### 2.1 主人要求（完整复述意图）

主人要求：面向**新的、更详细、更具体的**浏览器网页前端同步需求，以及**多用户组**需求，用**更安全、更高效**的写法，**重构底层**（不是只在现有轮询上打补丁了事）。

### 2.2 「更安全」在本文中的完整含义

1. **用户组边界：** 用户组 A 的设置变更通知、主页上的流式监视内容，**不得**泄漏到用户组 B 的主页流式区域；即使两边各有一张指向同一游戏身份的游戏账号卡片，**主页**上的流式监视仍按用户组隔离（详见 §5）。  
2. **游戏身份边界：** 真正打游戏服务器的互斥，仍按**游戏身份**（渠道 + 引继）互斥，防止同一真实号被两个任务同时打服（现有 TaskGate 方向正确，须在重构中保持并文档化）。  
3. **敏感字段：** 浏览器网页前端的账号列表 API **不得**为了跨组匹配进度而回传明文引继码；应使用内部键 + 对外 `game_id_hash`（或等价不可逆短指纹）做展示匹配。  
4. **设置真源：** 设置的权威内容是**数据文件夹**里该用户组文件中该游戏账号卡片的配置；各浏览器标签只是视图。自动保存成功后，同用户组、同游戏账号卡片的其它标签应能同步到磁盘上的新内容（通知 + 配置拉取）。  
5. **对游戏服务器：** 重构 UI 与状态层时，**不得**为调试向游戏服务器发送明显不符合客户端规范的请求体（NORMS **P27**）。

### 2.3 「更高效」在本文中的完整含义

1. **分层订阅：** 程序运行面板终端的高阶完整流、用户组主页的精简监视条、游戏账号卡片设置页的进度条，**轮询或推送的频率与载荷不同**；不得在用户关闭主页监视时仍为「看不见的面板」维持与高阶流同等密度的请求。  
2. **按需开启：** 主页上面向账号的精简监视，应允许用户**选择打开或关闭**（可点、可关），关闭后停止该主页相关的流式拉取。  
3. **身份聚合一次、多处投影：** 进程内对「某游戏身份正在跑什么」应有一份权威运行态（现有 RunHub 按 account_key 的方向），浏览器网页前端各页面只做**过滤投影**（按用户组过滤主页流；按游戏身份投影设置页进度条），避免每个标签各自发明一套忙闲逻辑。  
4. **不因「省性能」砍掉必要状态字段**（NORMS **P26**）：电脑不差这点开销；该独立的模块级「某某功能运行中」必须能表示，不得为了少几个字符串合并成含糊的一种状态。

### 2.4 与现状的差距（诚实 · 供重构对照）

截至 2026-08-07 源码与点测：

- 设置页约 1.5 秒配置轮询 + 设置通知落盘已有；**并非**所有页面都统一按「用户组 + 游戏账号卡片」做完整通知订阅。  
- RunHub 按渠道+引继聚合进度；主页卡片匹配曾主要靠别名，后补 `game_id_hash` 方向，**跨组主页文案「在用户组 A 中运行中」尚未按主人完整规格实现**。

## 3. 程序运行面板终端（本体）— 完整规格

### 3.1 主人要求（完整条件）

1. **程序本体的运行面板**（本文称**程序运行面板终端**）要能**显示完整内容**，面向**高阶用户**做监视与排查。  
2. 在**非异常状态**下：用户**不可以输入**、**不可以控制**任务（不可在此面板上点暂停/继续/放弃等控制；也不可当聊天式输入框使用）。它**仅用于查看与监视**。  
3. **关闭方式：** 用户直接点窗口的关闭按钮（叉掉）即可；**不需要**为关闭再做二次确认弹窗（主人明确：二次确认没有手动点叉关闭方便）。异常路径（例如端口被占用必须换端口、跨路径占用必须输入「我已知晓」）**不属于**「非异常状态」，仍允许并必须在程序运行面板终端完成必要的中文确认与输入。  
4. 提示内容分为两类，必须能区分：  
   - **本体专有**提示：与「整个程序进程 / 数据文件夹 Owner / 端口 / 双版本 / 占用锁」相关，不绑定某一个用户组或某一张游戏账号卡片。  
   - **面向特定用户组账号**的提示：与「某一用户组里某一游戏账号卡片上正在跑的任务」相关，可以是清日常整体，也可以是其中某一个功能模块正在运行；内容可以比主页精简条更完整。  
5. **面向特定用户组账号**的那一类提示，在精简之后，可以显示在**该用户组的主页**上，用于监视；主页上的展示必须支持用户**选择性点击打开**和**关闭**。  
6. **之前的进度条**是面向**不懂技术的用户**的（设置页 / 卡片附近那类简单进度）；**新的完整面板流**是面向**高阶用户**的。两套目的不同，不得用「一个进度条」混充「完整监视流」。  
7. **非同一用户组**时：即使两边具有**相同游戏身份**的游戏账号卡片，**主页上的面板窗口也不会显示其它用户组的流式数据**。  
8. 但是：**游戏账号卡片设置界面里的进度条**，对同一游戏身份，**会保持同步**（设置页进度条跟游戏身份；主页流式监视跟用户组隔离）。  

### 3.2 与旧任务书 PLAN_RUN_PANEL_AND_THEME 的关系

旧任务书讨论的是：浏览器网页前端里把「运行条」从折叠改成「是否开启」、默认关以省轮询。  
主人新规格**并未取消**「可关监视」的方向，但**大幅扩展**了：

- 完整流优先落在**程序运行面板终端**（高阶、只读、叉掉关闭）；  
- 主页只放**精简、可选开关**的账号监视；  
- 设置页进度条服务小白与跨组同步。  

因此实现时应**以本节为准**合并或取代旧 C07 的窄规格；旧文档保留为史，并在任务书中声明合并关系。

### 3.3 异常状态（允许输入）完整列举（可随实现增补，增补须改本文）

以下情况**允许并要求**在程序运行面板终端交互，不属于「非异常只读」：

1. 监听端口无法绑定：先完整中文确认「我知道端口被占用」，再由用户**自己输入**端口数字（程序不代填推荐号），成功后写入数据文件夹持久保存。  
2. 跨路径 / 云盘占用心跳未过窗口：用户输入完整短语「我已知晓」后方可强制启动。  
3. 数据文件夹已被同机其它进程占用（Owner 锁失败）：应说明情况并**退出**；**禁止**自动结束其它进程（尤其禁止自动结束普通版以免中断清日常）；开发版若因独占能力（如 wire）抢锁失败，应说明请用户手动叉掉已开窗口后再开开发版。

## 4. 浏览器网页前端：主页精简监视与设置页进度条

### 4.1 用户组主页上的精简监视

1. 内容来自「面向特定用户组账号」的任务信息，但**精简**于程序运行面板终端的完整流。  
2. 用户可以**选择**是否打开该监视；可以关闭。关闭后不应继续为该主页维持同等轮询。  
3. 仅显示**本用户组**相关的账号监视；**不得**把其它用户组的流式数据画到本用户组主页的监视窗口里。  

### 4.2 游戏账号卡片设置界面的进度条

1. 面向不懂技术的用户，继续提供清晰的进度条/简单状态。  
2. 对**同一游戏身份**，无论用户从用户组 A 还是用户组 B 打开「游戏账号甲」的设置页，进度条应反映**该游戏身份上正在进行的任务进度**（跨用户组同步）。  
3. 这与主页「不显示其它用户组流式数据」**同时成立**：主页隔离的是**用户组维度的流式监视窗口**；设置页进度条跟的是**游戏身份**。

## 5. 多用户组 · 同一游戏身份 · 游戏账号卡片 UI 区分（完整条件）

### 5.1 场景定义

- 存在用户组 **A** 与用户组 **B**。  
- 两边都有指向**同一游戏身份**的游戏账号卡片（主人举例中的「游戏账号甲卡片」：同一真实游戏号，可能别名相同或不同，但渠道+引继相同）。  
- 在用户组 **A** 中对该游戏身份启动了清日常，或启动了清日常中的某一个具体功能模块。  

### 5.2 用户组 A 的主页 · 游戏账号甲卡片

必须显示**本用户组内**的任务态，且粒度不止「清日常」一种：

- 可以是 **「清日常运行中」**；  
- 也可以是 **「某某功能运行中」**（例如快速刷图、魔女召唤、领取任务等模块级状态，具体中文名用模块产品名）；  
- 实现时状态枚举应可扩展，**不要**做成只有「清日常运行中」一个字符串。  

### 5.3 用户组 B 的主页 · 同一游戏身份的游戏账号甲卡片

- **不得**把用户组 A 的流式明细整段画在 B 的主页监视流里。  
- **应当**显示完整语义类似：**「在用户组 A 中正在运行」**（或实现时更通顺的完整中文，但必须表达：运行发生在**另一用户组**，且能指明是哪个用户组）。  
- 若实现时命名调整，必须在本文件修订表记录旧名→新名，并保证 A/B 不对称语义不变。  

### 5.4 设置页

见 §4.2：两边打开同一游戏身份的设置时，进度条保持同步。  

### 5.5 服务器角标

主人要求：游戏账号卡片上将用更显眼的 **EN、JP、TW** 表示该卡片配置在哪个服务器（渠道）。  
实现时：

- 日服显示 **JP**；国际服显示 **EN**；台服显示 **TW**（即使登录未就绪，卡片上仍应标 TW，并与「不可登录」提示并存，避免用户看不出渠道）。  
- 未知渠道显示完整 channel 标识，不得空白。  
- 样式须**显眼**（相对旧版小字 muted 渠道文案加强），具体 CSS 实现时定，但验收以「扫一眼能分辨」为准。

## 6. 与语义假成功修复的关系（完整交叉引用）

多用户组 UI 重构**不**免除下列已记录假成功问题（详见 [logs/2026-08-07-known-issues-before-fix.md](../logs/2026-08-07-known-issues-before-fix.md)）：

1. **登录奖励：** `get_home_info` 返回的 `loginBonusDataList` 为空时，不得再显示「已领取登录奖励」成功；应跳过并说明今日已无可领。非空时才可成功，并尽量摘要。  
2. **活动扫荡：** `todayPlayableCount` 全 0 且未发生战斗/skip 请求时，不得显示空成功「活动扫荡 队伍=…」；应跳过并写清原因；成功时必须能回答扫了哪些活动。  
3. **活动剧情：** 主人确认「ひとりの時間」两段在约 11 点新开后阅读为正确；已读重复标成功须修。  

主页上的「某某功能运行中」文案，应与模块真实状态机一致，不得在模块已假成功结束时仍显示运行中，也不得在未运行时显示运行中。

## 7. 程序运行面板终端 · 端口与占用（已实现要点完整收录）

下列已在实现中或规格中钉死，供与 §3 对照，避免重构时回退：

1. 同机同一数据文件夹：`owner.lock` 独占；第二进程无条件退出。  
2. 跨路径占用：`occupancy_heartbeat.json` 独立文件；判定**数据文件夹路径**；约 30 分钟窗口；强制短语「我已知晓」。  
3. 端口：数据文件夹可无端口字段则用默认；绑定失败则「我知道端口被占用」→ 用户自填端口 → 写入数据文件夹。  
4. 开发版不得自动 taskkill 普通版；仅提示用户手动叉掉窗口。  

更名到 `RustMadoka_data` 后，上述文件均位于新数据文件夹下，逻辑不变。
