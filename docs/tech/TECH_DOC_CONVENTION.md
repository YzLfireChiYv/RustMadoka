## 1. 规则

1. **产品新代码**（`crates/`、`apps/android` 产品路径）必须有完整注释：职责、输入输出、不变量、边界、与协议/产品关系。  
2. **Outbound：** 代码或模块文件头注释写明对应文档路径（如 `docs/tech/SDK_AND_LOGIN.md`）。  
3. **Inbound：** 技术文档写明对照源码路径（如 `crates/rustmadoka-core/src/gree.rs`）。原版优先写可核对路径：`archive/...` 与/或说明「权威树 `origin/main` @ hash」。  
4. 在 A 新增对 B 的引用时，尽量同时改 A 的 Outbound 与 B 的 Inbound。  
5. 归档树 `archive/` 可只写分析注释；**不**当产品主工程堆功能。  
6. 文档结论分档：静态钉死 · 探路已证 · **【实测预留】** / 未证实。  
7. **禁止用简写冒充完整技术文档。** 分类摘要、一页总览可以存在，但必须标明「摘要」并链到**穷尽或逐步对照源码**的正文；不得在正文用「详见源码」代替应落盘的步骤、字段表、路径表。  
8. **每次编写或大改技术文档必须打开对应源码**（原版与/或 Rust），按文件/函数/字段书写；禁止只凭记忆扩写。  
9. **语言：** 允许纯中文、纯英文、或中英对照（同一文件分节或双列表格）。服务主人理解时优先中文完整句；协议常量/API 路径/字段名保持与源码一致的英文标识。  
10. **避免假绝对（NORMS G7 · 主人钉死）。** 技术文档里的机制描述、映射表、攻略对照、能力矩阵，默认都是**带证据范围的当前认识**，可以被后继源码/真机/新导出**纠正**。  
    - **应写：** 「本机某次 mst 样本」「静态对照 origin @ hash」「假说，待点测」「与攻略站名词暂作对照，未证明枚举一一对应」。  
    - **慎写 / 禁止当真理：** 「必然」「永远如此」「一定就是 X」「游戏只有这些内容」「协议保证…」——除非有可复核的硬约束（且仍建议写清约束来源）。  
    - **已写错时：** 后继 AI **应当**在发现异常时质疑并改文档；禁止因「文档已经写死」而压抑证伪。  
    - 与 §1.6 分档一致：静态对照 · 探路已证 · 【实测预留】· 假说 · 已证伪。  

**为什么（§1.1–1.9）：** 跨会话 AI 与人靠落盘导航；断链与假完整会导致改错层、重复踩 L1/L2、漏掉可产品化的底层数据。  

**为什么（§1.10）：** 文档若用绝对语气包装未穷尽结论，后继模型容易把文档抬到与真机/源码同级甚至更高，**看到矛盾也不敢改**，错误会跨会话固化。可质疑、可标「可能错」的文档，才与 MAY CONTAIN ERRORS 一致。

## 2. 推荐文档头

```markdown
# 标题

| 项 | 内容 |
|----|------|
| **墙钟** | YYYY-MM-DD |
| **Outbound** | `crates/.../file.rs` · `archive/...` 或 origin/main 路径 |
| **Inbound** | HANDOFF · NORMS · 谁引用本文 |
| **MAY CONTAIN ERRORS** | Yes — 以源码与真机为准 |
```

## 3. 推荐代码头（Rust）

```rust
//! 一句话职责。
//!
//! - 文档: docs/tech/XXX.md
//! - 对照: archive/pre-rust-2026-08/...（若有）
```
